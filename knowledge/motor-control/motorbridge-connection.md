# MotorBridge 连接入口与设备参数

日期：2026-10-11。对应 S1-002。依据本机 MotorBridge **0.5.6** 的 `motorbridge/core.py`、`motorbridge/__init__.py` 和本仓库接口基线整理。

本课只做源码阅读、参数辨析和离线代码骨架。**不连接适配器或电机，不执行任何通信调用。**

> **阅读方式**：第一次只读第 1～4、7～13、15～17 节，理解“怎样建立单电机控制所需的连接对象”。第 5、6、14、18 节属于源码依据与排错参考，不要求背诵，不进入本课考核。课程主线是使用 MotorBridge 控制电机，底层 ABI 和指针不是当前学习目标。

## 1. 学完后要能解决什么问题

假设以后已经确认了一台串口适配器和一台达妙电机，你需要知道：

1. 用哪个 `Controller` 入口打开通信连接。
2. 这个入口需要哪些参数，参数从哪里取得。
3. 怎样把一台达妙电机添加到这个连接上。
4. 哪一步只是“在软件里创建句柄”，哪一步真的会访问设备。
5. 当前哪些值已有证据，哪些值必须继续保持未知。

今天的结果不是“电机已经连上”，而是形成一个参数明确、不会自动运行、以后可以继续验证的调用骨架。

## 2. 本课必会与本课不考

### 本课必会

1. 读懂 `Controller.from_dm_serial(serial_port, baud)` 的两个输入、返回对象和调用副作用。
2. 读懂 `controller.add_damiao_motor(motor_id, feedback_id, model)` 的三个输入和返回对象。
3. 区分导入类、定义函数、调用函数三个时刻，知道哪一步会接触底层通信。
4. 区分 SDK 默认值、教程示例值和当前设备已经确认的真实值。
5. 说明为什么 `add_damiao_motor()` 不是扫描电机，也不是修改电机内部 ID。

### 本课不考

- `request_feedback()`、`poll_feedback_once()` 和 `get_state()` 的新鲜度与缓存语义；这些属于 S1-003。
- 使能、失能、运动、模式切换、异常清理和急停设计。
- CAN 报文位布局、寄存器地址、修改 ID、设置零点或持久化参数。
- 背诵本机端口、波特率、ID 或模型键；这些值尚未取得完整设备证据。
- `Controller` 的完整退出状态机；本课只知道它持有资源，详细生命周期在 S1-005 学习。

## 3. 先看完整调用链的位置

以后真实读取状态时，调用链大致是：

```text
确认通信参数
    ↓
创建 Controller
    ↓
添加 Motor
    ↓
请求反馈
    ↓
轮询通信
    ↓
读取 MotorState
```

S1-001 已经学习最末端的 `MotorState` 显示。S1-002 回到前两步，只学习怎样形成 `Controller` 和 `Motor`。后面三步今天只作为位置预告，不写、不运行、不考核。

## 4. Controller 到底是什么

`Controller` 不是电机本身，也不是一组普通配置字段。它代表一个实际通信入口，并保存底层控制器指针。

可以把它理解成：

```text
一条通信链路的拥有者
├─ 知道通过哪种传输方式通信
├─ 持有底层资源
├─ 在这条链路上添加一个或多个 Motor
└─ 负责轮询、总线级操作和最终资源释放
```

一个 `Controller` 可以管理这条链路上的电机句柄。`Motor` 则代表其中一台已登记设备的操作入口。不要把二者混成一个对象：连接级操作属于 `Controller`，单台电机操作属于 `Motor`。

## 5. 选读：为什么不能直接写 Controller()

本机 0.5.6 提供多个连接入口：

| Python 入口 | 源码表示的传输方式 | 典型参数 | 本课是否使用 |
|---|---|---|---|
| `Controller(channel)` | SocketCAN | `channel="can0"` | 否 |
| `Controller.from_socketcanfd(channel)` | SocketCAN FD | `channel="can0"` | 否 |
| `Controller.from_dm_serial(serial_port, baud)` | 达妙串口入口 | 设备路径、波特率 | **本课重点** |
| `Controller.from_mcu_serial(serial_port, baud)` | MCU 串口入口 | 设备路径、波特率 | 否 |
| `Controller.from_dm_device(dm_device_type, dm_channel)` | 达妙设备运行时入口 | 设备类型、通道 | 否 |

这些入口不是不同写法的同一个东西。它们会调用不同的底层构造函数。选择错误入口时，即使参数类型正确，也可能完全无法使用实际适配器。

当前课程选择 `from_dm_serial()` 是为了学习用户此前代码中出现的达妙串口调用形状。它不证明现场适配器一定属于这种入口；首次真实连接前仍需核对适配器型号、驱动和系统设备节点。

## 6. 选读：从源码确认 from_dm_serial()

本机源码中的公开签名是：

```python
@classmethod
def from_dm_serial(
    cls,
    serial_port: str = "/dev/ttyACM0",
    baud: int = 921600,
) -> Controller:
    ...
```

逐项解释：

### `@classmethod`

这个入口挂在类上，所以写成 `Controller.from_dm_serial(...)`。不需要先有一个 `Controller` 实例。调用成功后，它创建并返回新的 `Controller`。

### `serial_port: str`

这是底层要打开的设备路径字符串。源码会对它执行 `.encode()`，再传给本地 ABI。

`/dev/ttyACM0` 只是函数签名里的默认字符串。它常见于部分 Linux 串口设备，但不能证明：

- 当前电脑一定存在这个路径；
- 这个路径一定对应目标适配器；
- 用户具有访问权限；
- 适配器驱动和固件与 MotorBridge 兼容。

真实值应来自当前操作系统的设备枚举、适配器身份和受控核对，不能从历史代码复制后标记为已确认。

### `baud: int`

这是交给底层串口入口的波特率整数。源码会执行 `int(baud)` 后传入 ABI。

`921600` 是 SDK 默认值。它说明“调用者省略参数时，SDK 会尝试使用这个数字”，不说明现场适配器当前必然使用它。填错时可能导致打不开通信、无法交换有效数据，或者产生难以解释的超时。

波特率是 **bit/s** 量级的串行通信速率参数。今天只理解它的作用，不要求推导串口时序或误差容限。

### `-> Controller`

这是返回类型。成功时得到通信控制对象；失败时不会返回一个“半成功”的普通配置对象。

### 源码实际做了什么

Python 层按以下顺序工作：

```text
创建未初始化的 Controller Python 对象
    ↓
取得本地 ABI
    ↓
把 serial_port 编码、把 baud 转成整数
    ↓
调用底层 motor_controller_new_dm_serial(...)
    ↓
检查返回的底层指针
    ├─ 指针有效：保存指针并返回 Controller
    └─ 指针无效：抛出 CallError
```

因此，“调用 `from_dm_serial()`”本身就是有副作用的硬件入口。路径错误、权限不足、底层库不可用或设备不兼容都可能在这一步失败。

## 7. 导入、定义和调用不是同一件事

初学时最容易把下面三种行为混在一起。

### 只导入类型

```python
from motorbridge import Controller, Motor
```

这让 Python 名字可用。它不是创建 `Controller`，也没有把某个电机添加进来。

### 只定义函数

```python
def open_dm_serial(serial_port: str, baud: int) -> Controller:
    # 函数体只有未来被调用时才执行
    ...
```

Python 读取函数定义时会创建函数对象，但不会执行函数体。今天的练习利用这一点：可以写出真实调用结构，同时保持不执行。

### 真正调用函数

```python
controller = open_dm_serial(...)
```

这时函数体才会运行。如果函数体调用 `Controller.from_dm_serial()`，程序就会进入底层连接流程。今天没有这一步的授权和前置条件，所以练习文件不能在模块顶层或 `main()` 中调用它。

## 8. 逐行读懂 add_damiao_motor()

本机源码中的公开签名是：

```python
def add_damiao_motor(
    self,
    motor_id: int,
    feedback_id: int,
    model: str,
) -> Motor:
    ...
```

调用形状是：

```text
已有并且仍处于打开状态的 Controller
    ↓
controller.add_damiao_motor(motor_id, feedback_id, model)
    ↓
Motor
```

源码依次执行：

1. `_require_open()`：确认 `Controller` 仍持有底层指针。
2. 把 `motor_id`、`feedback_id` 和编码后的 `model` 交给底层达妙电机添加函数。
3. 检查底层是否返回电机句柄。
4. 成功时把句柄包装为 `Motor`；失败时抛出 `CallError`。

### `motor_id: int`

这是添加达妙电机时传给底层的目标电机标识参数。它参与软件如何指向目标设备，但 Python 包装层没有在这里说明完整 CAN 映射，也没有为达妙调用做显式范围检查。

因此不能根据“类型是 int”就认定任何整数都安全有效，也不能只看历史示例中的 `0x01` 就认定当前电机 ID 是 1。

### `feedback_id: int`

这是同时传给底层的反馈标识参数。它与接收方向有关，但本地 Python 包装层没有给出达妙协议中完整的仲裁 ID 计算和设备配置规则。

本课只要求确认两点：

1. 它与 `motor_id` 是两个独立参数，不能无依据认为一定相同。
2. 真实值和精确定义需要对应型号协议、设备配置或受控实验支持。

### `model: str`

这是传给底层驱动的型号键字符串。Python 会执行 `model.encode()`，但不会在这一层列出全部合法键。

项目 PDF 声明电机是 **DM4310P**，这是设备型号线索；历史代码使用过 `"4310"`，这是示例线索。二者尚不足以证明 MotorBridge 0.5.6 对当前设备要求的模型键一定是 `"4310"`。真实映射必须由匹配版本的驱动资料或验证证据确认。

### 返回的 `Motor`

返回值是一个软件句柄，用于以后发出单电机请求或读取状态。创建句柄不等于：

- 已经扫描到真实电机；
- 已经收到反馈；
- 电机已使能；
- 电机参数正确；
- 电机已经安全可运动。

这些结论都需要后续独立证据。

## 9. 添加电机、扫描电机和修改 ID 的区别

三者是不同操作：

| 操作 | 含义 | `add_damiao_motor()` 是否完成 |
|---|---|---|
| 添加软件句柄 | 告诉当前 Controller：以后按这些参数操作一个达妙电机 | 是 |
| 扫描设备 | 主动发现总线上有哪些设备及其身份 | 不是 |
| 修改真实电机 ID | 改写设备自身的通信配置 | 不是 |

`add_damiao_motor()` 接受你给出的参数。它不会自动证明这些参数正确。即使函数返回 `Motor`，也可能只是底层成功创建了句柄，不能据此声称真实设备在线。

## 10. motor_id 与 feedback_id 为什么不能随便填

控制通信至少涉及两个问题：

```text
软件发出的命令应该指向哪个设备？
设备返回的信息应该按什么身份识别？
```

MotorBridge 的达妙添加接口要求同时给出 `motor_id` 和 `feedback_id`，说明底层需要两项身份信息。但仅靠 Python 参数名，还不能可靠推出具体协议位布局或当前设备配置。

因此本项目采用以下证据顺序：

1. 先记录 Python API 的参数名和类型。
2. 再查匹配型号、固件和适配器的协议或配置资料。
3. 在满足硬件安全条件后，用受控实验验证实际收发身份。
4. 证据一致后才写入项目配置并标记“已确认”。

如果两个 ID 填错，可能出现无响应、读取到别的设备、身份冲突或错误归属等问题。当前没有足够证据判断会出现哪一种，因此不能用猜测替代验证。

## 11. 参数表应该怎样填写

本课需要整理六项：

| 参数 | 类型/单位 | SDK 已知信息 | 当前设备事实 | 还需要什么证据 |
|---|---|---|---|---|
| `serial_port` | 字符串路径 | 默认 `/dev/ttyACM0` | 未知 | 当前系统设备节点与适配器身份 |
| `baud` | 整数，bit/s | 默认 `921600` | 未知 | 适配器文档、配置或匹配版本资料 |
| `motor_id` | 整数标识 | 必填；Python 层无达妙范围校验 | 未知 | 电机配置、协议或受控识别 |
| `feedback_id` | 整数标识 | 必填；传给底层达妙驱动 | 未知 | 对应协议定义与实际设备配置 |
| 电机型号 | 型号名称 | 不由该函数自动检测 | PDF 声明 DM4310P；铭牌待核对 | 铭牌或采购/设备资料 |
| SDK `model` 键 | 字符串 | 必填并编码传给底层 | 未知 | MotorBridge 0.5.6 对应型号映射 |

填写时要区分四种状态：

- **已确认**：有当前设备的一手证据。
- **候选**：有匹配资料，但还没有在当前设备上核对。
- **示例**：只来自教程或历史代码。
- **未知**：目前没有足够依据。

任务提交表中只使用“已确认 / 未知”作为最终状态；候选和示例写进证据说明，但不能冒充已确认。

## 12. 为什么默认值不等于真实值

默认参数解决的是编程便利性：调用者不传值时，函数仍有一个可以尝试的输入。它不是设备检测结果。

```text
SDK 写着默认 /dev/ttyACM0
           ≠
系统已经证明目标适配器就在 /dev/ttyACM0
```

设备节点可能随插拔顺序变化；波特率可能与适配器配置不一致；ID 可能被修改过；同系列电机的 SDK 模型键也可能需要精确映射。工程上必须记录“这个值从哪里来”，而不只记录“这个值是多少”。

## 13. 本课代码应该长成什么结构

学习者文件只建立两个边界：

```text
open_dm_serial(明确传入的路径, 明确传入的波特率)
    └─ 转交给正确的 Controller 类方法

add_damiao_motor(已打开的 Controller, 三个明确参数)
    └─ 转交给 Controller 上的达妙添加方法
```

代码结构应满足：

- 使用公开类型 `Controller` 和 `Motor`。
- 函数参数全部由调用者提供，不在本课里猜测真实设备值。
- 函数返回 SDK 对象，不隐藏异常、不静默回退到其他传输方式。
- docstring 明确写出调用会访问真实通信资源。
- 模块导入后只得到函数定义，不自动建立连接。

讲义不给出两个函数的完整函数体；具体实现由学习者依据真实签名独立完成。

## 14. 选读：失败路径来自哪些层

今天只需要知道错误可能在哪一层出现：

```text
参数错误
  ↓
设备路径或权限错误
  ↓
ABI / 驱动 / 适配器错误
  ↓
底层无法创建 Controller → CallError

Controller 已关闭或参数不匹配
  ↓
底层无法创建 Motor → CallError
```

今天不要求捕获这些异常，因为随意捕获后继续运行可能隐藏真实问题。练习函数直接保留 SDK 的失败行为，后续生命周期和故障处理任务再设计恢复策略。

## 15. 常见错误

### 错误一：在模块顶层连接

```python
controller = Controller.from_dm_serial(...)
```

这样只要导入文件就会尝试访问硬件，不适合作为今天的离线练习。

### 错误二：把示例参数标成设备事实

历史代码能运行或网上示例常见，不等于当前电机、适配器和系统配置一致。

### 错误三：认为 add 就是 scan

`add_damiao_motor()` 使用调用者给定的参数创建句柄，没有在 Python 接口中返回“发现了哪些设备”。

### 错误四：认为返回 Motor 就证明在线

句柄创建成功与真实反馈成功是两个验证层级。后者需要请求、轮询、状态和身份的独立证据。

### 错误五：为了防错直接调用 disable()

`disable()` 本身也是硬件命令，需要正确连接、正确身份和授权。它不是离线检查，也不能替代实体急停。

### 错误六：捕获所有异常后返回 None

这会把路径、权限、ABI 或参数错误隐藏成一个模糊空值。本课保持 SDK 异常可见。

## 16. 今天允许和禁止的验证

### 允许

- 阅读本机 MotorBridge 0.5.6 Python 源码。
- 编写函数定义和类型标注。
- 用 `compile()` 检查源码语法；`compile()` 只编译文本，不执行模块。
- 静态搜索是否误写使能、运动、反馈或持久化调用。
- 审查参数表的证据等级。

### 禁止

- 实例化 `Controller`。
- 调用 `add_damiao_motor()`。
- 请求或轮询反馈。
- 使能、失能、运动、模式切换。
- 修改 ID、零点、固件、寄存器或持久化参数。
- 把 `finally`、`close()` 或 `disable()` 当作已经具备实体安全条件。

## 17. 本课完成后仍然不知道什么

完成 S1-002 后，仍然不能声称：

- 当前串口路径和适配器可用；
- 当前波特率正确；
- 电机 ID 与反馈 ID 已确认；
- `DM4310P` 与 SDK `model` 键映射已确认；
- 能收到新鲜反馈；
- 电机可以安全使能或运动。

这不是任务失败，而是证据边界。S1-002 的目标是把未知项暴露并记录，避免以后把猜测藏进代码。
