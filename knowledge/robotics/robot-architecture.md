## 先理解控制链路

“Python 程序运行成功”只能证明程序执行到了某一步。机器人控制涉及多层，每层都有自己的输入、输出和失败方式。本项目计划按以下职责组织：

```text
学习者编写的应用 / 后续 ROS 2 节点
    ↓ 调用控制与设备接口
robot_control 核心包：控制流程、设备适配、状态与校验
    ↓ 按已确认版本调用
MotorBridge SDK 及底层传输实现
    ↓ 经操作系统驱动与实际适配器
通信链路 → 电机驱动器 → 电机与机械负载
    ↑ 身份、状态与反馈需要沿链路返回
```

这是职责图，不是当前硬件接线图。适配器、传输方式、端口、固件、设备 ID 和负载尚待你盘点，不能把图中的箭头理解为连接已经成立。[本项目计划架构](../../engineering/architecture/system-overview.md)规定核心功能与 ROS 接入分开，纯数学模块可离线验证。

| 层次 | 你要先弄清的问题 | 可用的证据来源 |
|---|---|---|
| Python 环境 | 当前使用哪个解释器？包在哪个环境中？ | 本项目只读环境报告 |
| 项目核心代码 | 当前有哪些文件，哪些功能仍是规划？ | README、src/README.md、实际文件 |
| SDK | 参考的是哪个版本？元数据存在还是已经验证可调用？ | 元数据、版本对应源码及既有基线 |
| 通信设备 | 使用什么适配器和传输方式？ | 铭牌、已有设备资料；缺资料写待确认 |
| 电机与驱动器 | 具体型号、固件、ID、单位与限制是什么？ | 设备资料和后续实验；盘点不等于操作设备读取参数 |
| 机械部分 | 是否有减速机构、固定、负载和行程约束？ | 现场已有资料或待确认项 |

MotorBridge 官方仓库分别提供 Python 绑定和底层接口等组成部分。此处只将其作为软件层的参考入口，不执行仓库中的总线配置、扫描或运动示例，也不把远端最新接口当作本地版本接口。[官方仓库](https://github.com/motorbridge/motorbridge)

## 为什么先确认 Python 环境

虚拟环境有自己的解释器入口及包安装位置。本项目使用 `.venv/bin/python` 明确选择项目环境；终端里的 `python3` 可能解析到另一个环境。环境之间的包版本不能直接互相代入。[Python 3.12 venv 文档](https://docs.python.org/3.12/library/venv.html)

本项目的 [check_environment.py](../../scripts/check_environment.py) 使用标准库读取当前解释器、平台、包元数据及 PATH 中的命令位置。它没有导入 MotorBridge 或打开设备。

| 报告字段 | 应怎样理解 |
|---|---|
| python_executable | 这次实际运行的解释器路径 |
| python_version | 这个解释器的 Python 版本 |
| platform / machine | 这次报告所处系统和机器架构 |
| packages | 当前解释器可发现的包元数据；null 表示本次没有找到相应分发包元数据 |
| commands_on_path | 当前 PATH 可找到的命令位置；空值不证明其他环境也没有安装 |
| scope / notes | 报告能证明什么，以及不能证明什么 |

“有包元数据”“能导入”“能建立通信”“收到可识别反馈”“完成真实动作”是不同证据层级。只完成第一项时，不能把后面几项也写成通过。

## 设备事实怎样记录

一条可追溯的事实至少包含：**对象、字段、值、单位或格式、来源、核对时间和状态**。未知不是零，也不是默认值。资料缺失时写“待确认”，同时写清以后需要什么资料才能确认。

例：协议示例里出现某个 ID，只能说明示例使用了该值。它不能证明你手中电机使用同样的 ID。原 PDF 声明有一台 DM4310P，也不能替代对实际铭牌、固件和设备条件的核对。

本讲不推导控制公式，也不确定数值限幅。先保留字段语义：角度、速度、电流或力矩应分别记录单位和来源；电机轴与输出轴的定义、方向、零点和减速比未确认时不要换算。CAN bit/s 与串口 baud 分开记录，不能仅因数值相同就认为含义相同。
