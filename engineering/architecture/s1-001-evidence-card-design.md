# 设备证据卡：首次真实连接前的参考

日期：2026-10-10。原 S1-001 的资料设计，现保留为首次硬件准备参考。用户要求从 MotorBridge 开始，[今日任务](../../learning/daily/2026-10-10-S1-001.md) 已修订；本页不再是今天的作业，示例日期按实际采集日调整。

## 输入、处理与输出

```text
当前项目解释器 → 只读环境脚本 → 原始 JSON 报告
已有设备资料 → 学习者核对来源 → Markdown 设备证据卡
理论讲义 + 上述证据 → 学习者的链路解释与问题回答
```

保留原始 JSON 可以防止解释过程改变原始报告。Markdown 证据卡负责解释报告、整理设备资料、记录未知项和确认计划。每日任务卡只记录本次过程并链接提交物，避免把同一事实反复抄写到多个地方。

## 未来资料接口

首次真实连接前再按实际日期命名并安排以下资料，当前无需创建：

| 文件 | 输入 | 应包含的输出 |
|---|---|---|
| engineering/hardware/YYYY-MM-DD-environment.json | 本项目 .venv 运行 check_environment.py | 脚本原样输出的 JSON，不能手改成预期版本 |
| engineering/hardware/YYYY-MM-DD-device-evidence.md | 原始 JSON、已有铭牌/资料、你的核对 | 环境解释、设备证据表、链路图、未知项、下一步 |

证据卡建议使用以下结构，由你填内容：

1. 日期、任务 ID、记录人及本次范围。
2. 环境报告的相对链接；解释解释器路径、版本、平台、motorbridge 元数据及命令可见性。
3. 设备证据表：对象 / 字段 / 当前值或待确认 / 单位或格式 / 来源及定位 / 核对日期 / 状态。
4. 你理解的通信链路，并在每一层标注已确认或待确认。
5. 尚缺什么，以及每项应从哪里确认。
6. 本次执行过的命令、遇到的问题和没有执行的硬件活动。

设备表至少覆盖：电机型号与数量、固件、适配器型号与传输方式、系统/驱动、通道或端口、CAN 速率、串口速率（不适用则说明）、Motor ID、Master/Feedback ID、供电、固定/负载、停止方式；涉及减速机构或关节模型时另记轴、单位、零点和方向的未知项。盘点时不要求立刻把所有未知都解决，但要显式列出，不从示例复制参数。

## 异常与边界

- 脚本不存在、项目解释器无法执行或报告不能解析：保存错误文字，任务保持未完成，先定位环境问题。
- 包元数据为空：这是原始观察值，结合报告范围解释；不为消除空值而临时安装依赖。
- 没有设备资料：填写待确认、缺失证据及确认方式，不编造型号、ID 或安全限制。
- 同名输出已经存在：先阅读，补充或复用，不覆盖已记录的证据；命令使用防覆盖重定向。

资料整理只读环境与已有资料，不打开总线、使能电机、修改 ID 或执行运动。后续业务代码的接口和异常用例在 S1-003～S1-005 逐步设计。

## 怎么验收

检查 JSON 可解析、命令可追溯、证据卡栏目完整、事实与未知可区分、来源可以定位、链路解释来自你的理解。将来相关任务具体安排文件与问题，不能据本参考向用户催交首日盘点。
本次验收是文档与环境证据复核；没有业务实现时不编造代码审查，也不据此判 S1 阶段通过。
